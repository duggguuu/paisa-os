# Paisa OS: rules for changing this app

This app is **live with real financial data**. Production = Render web service (free plan), deployed automatically on every push to `main` of the private repo `duggguuu/paisa-os`. The data lives in a **Neon Postgres** database, which is separate from the code. Deploys replace code, never data.

## Golden rules (data safety)

1. **Never edit or delete a file in `db/migrations/` once it has been pushed.** Change the schema by adding the next numbered file (`002_…sql`, `003_…sql`). `migrate()` checks every applied file's checksum and refuses to start if one was edited. On Render a failed start keeps the previous version live, so this protects the data, but it also blocks the deploy.
2. **Migrations must be additive and safe on existing rows:** `create table`, `add column … default …` or nullable columns, new indexes, new views/functions. Each file runs in one transaction.
3. **Destructive changes** (drop/rename a column or table, changing types, rewriting data) need two steps and a backup:
   - Ship code that stops using the old column first, then drop it in a later migration.
   - Before anything that rewrites or deletes rows, take a backup: Settings → Export in the app, and/or create a Neon branch (a point-in-time copy) in the Neon console.
4. **Ledger invariants are enforced by the database. Don't weaken them:** postings per transaction sum to zero (deferred trigger), `audit_log` is append-only, and deleting a transaction voids it. Money is integer paise, never floats.
5. **Never commit secrets.** `DATABASE_URL`, `APP_SECRET` and Kite keys live only in Render's environment. `APP_SECRET` must never change, because it decrypts the stored Kite secret and signs sessions.
6. **Run `npm test` before every push.** It needs a throwaway Postgres (`TEST_DATABASE_URL`). The tests DROP the `public` schema of that database, so never point `TEST_DATABASE_URL` at Neon production.

## Working on it

- `npm run build` builds the web and API apps. `npm test` runs the API/ledger tests (real Postgres) plus the web voice-parser tests.
- Testing a risky migration against real data: create a Neon **branch** of production, run the new version locally against the branch's URL, check it, then delete the branch.
- The demo book (Settings → sample data) is fully separate from the real book. Use it to try UI changes on the live app.

## Layout

- `apps/api/src/`: Fastify API. Core files: `ledger.ts` (posting rules), `stats.ts`, `dashboard.ts` (net worth, safe-to-spend), `kite.ts` (read-only Zerodha), `db.ts` (pool + migrations). Feature modules: `recurring.ts`, `importer.ts` (statements), `cas.ts`, `splitwise.ts` (read-only), `insights.ts`, `goals.ts`, `planner.ts` (Budget Planner numbers, Financial Health score), `copilot.ts` (local engine; Claude only if `ANTHROPIC_API_KEY` is set), with routes in `routes-extra.ts`.
- Passkeys/app lock: `passkeys.ts` (@simplewebauthn/server). The RP ID comes from PUBLIC_URL/RENDER_EXTERNAL_URL, so changing the domain invalidates existing passkeys. `requireAuth` enforces the lock (HTTP 423); only the unlock, lock, status and logout routes accept a locked session. Lock = idle (`lock_minutes`) **or** lock-on-open: every login/unlock returns an `unlockKey` that the web app keeps in sessionStorage and sends as `x-unlock`; the session stores hashes of the last 8 (`session.unlock_keys`), so a new tab or a fresh app start is locked. Unlock with Face ID (phones), a 4–6 digit PIN (laptops: `/api/auth/unlock/pin`; set via `PUT /api/security/pin` with the password; 5 wrong tries pause it until a password unlock; it never logs in by itself) or the password (`/api/auth/unlock/password`). The lock screen picks the method by device (`isPhone()` in `components/Security.tsx`). Any raw `fetch` to /api must send `authHeaders()` from `lib.ts`.
- Stuff: `stuff.ts`, routes `/api/stuff/*`. Purchases create one expense and move Want → Own (matched by product code in the link, or by name). Sales create income and move Own → Sold. The 'Yash's Stuff' Claude Sheet can't be reached from the server; Claude syncs it through the Claude Docs connector when asked. OCR is on the device (`receipt.ts` `ocrImages`, which inverts dark screenshots); parsers are in `web/src/orders.ts`.
- Owe & owed (`debts.ts`, page `/debts`): typed balances are set exactly with an equity adjustment (never spending). Receivable `meta.segment` = person | lent | splitwise ("Splitwise (overall)"). Loans are `kind='loan'` accounts with meta {lender, type: emi|interest_only, rate, emi, emi_day, end_date}; interest-only payments are all interest (logged as an expense); `PUT /api/loans/:id` corrects a loan (adjusts principal today, updates its rule); the EMI is a monthly transfer rule, and logging it splits into principal + 'Interest paid' (spending) via `emiSplit`.
- FDs (`fds.ts`, page `/fds`): `kind='fd'` accounts, meta {bank, rate, start, maturity, compounding, fundedFrom (label), fundedFromAccountId, expectedMaturity (bank's figure, paise; overrides the formula and today's value grows toward it)}; ledger balance = principal, value today/at maturity is computed. `PATCH /api/fds/:id` edits; principal can change only for opening-balance FDs (transfer-funded ones keep the transfer). Rates: `fd-rates.ts` reads Paisabazaar's public FD table (GET, no user data, 12 h in-memory cache, bundled fallback dated 11 Nov 2026 — refresh `BUNDLED` occasionally); web maths in `apps/web/src/fd-math.ts` must match `fdValue`. Post Office schemes (`SCHEMES` in fd-rates.ts, India Post, reset quarterly: update with `SCHEMES_AS_OF`) carry compounding; `yearly_payout` = PO TD (quarterly, paid out yearly). FD meta also has `scheme` (label) and `bankAccountId` (FD held with one of your bank accounts → Accounts shows that bank as Savings + FDs). PATCH `fundFromAccountId` turns an opening-balance FD into a transfer out of that account. Account delete: `GET/POST /api/accounts/:id/delete` (preview, then app PIN — or login password if no PIN / PIN locked; wrong PINs share the unlock counter); deletes every txn touching the account, so counterpart balances change. Maturing posts bank +credited, FD −principal, 'Interest' income −interest (external_ref `fd:<id>`) and archives the FD.
- Salary (`salary.ts`, page `/salary`): `salary_profile` (earnings / deductions / employer lines, monthly paise) drives a monthly income rule for the take-home on `pay_day` (31 = last day). `salary_slip` per month holds TDS for the tax check. The New Regime tax engine is in `web/src/tax.ts` (rupees, tested in `web/test/tax.test.ts`); update its constants when a Budget changes slabs.
- Payslips: `web/src/payslip.ts` reads PDF/Excel/CSV/TXT payslips (two-column or stacked layouts, wrapped names, kinds, month/net/employer, total checks; tests in `web/test/payslip.test.ts`). The Salary page uploads several at once, saves each month's slip, and can set the monthly structure from the latest (arrears lines dropped). Money-in review can mark credits as Salary; credits whose text contains the employer's name are offered (and statement imports book them as Salary via `guessBooking`'s `employer`).
- Uploads: every file input goes through `web/src/files.ts` (`UPLOAD_ACCEPT` = PDF, Excel, CSV, TSV, TXT; images where OCR applies). PDFs become positioned rows (`pdfRows`, password prompt on locked PDFs); tables are aligned to their header with `pdfTableGrid`; Excel uses SheetJS (`xlsx` from cdn.sheetjs.com tarball, lazy chunk, bundled). `filesToTexts` = OCR for images + readers for the rest. Lists of checkboxes use `components/SelectBar.tsx` (Select all / Unselect all).
- Categories: defaults live in `books.ts` `DEFAULT_CATEGORIES` (new books); migration 009 adds any missing default category/subcategory to existing books by name (never renames or moves). When you add defaults, add a new migration the same way (generated from the list). Users manage categories at `/categories` (`POST /api/categories`, `PATCH /api/categories/:id` for name/icon/hide; hiding a parent hides its children; system categories in `SYSTEM_CATEGORIES` can't be hidden). New income subcategories inherit `not_income` from their parent.
- Mandates & subscriptions are recurring rules with `mandate` (type, UMRN, max amount…) and `reminders` [{daysBefore, hour}] (migration 010); `every` repeats every N cycles (quarterly = monthly + 3). Page `/mandates`; they also show in Bills & recurring.
- Notifications (`notify.ts`): Web Push with VAPID keys generated into `app_setting`; devices in `push_subscription`; prefs in `app_user.notify_prefs` (three daily nudges, amounts off by default). The free server can't wake itself, so `.github/workflows/reminders.yml` calls `POST /api/cron/tick` hourly with `x-cron-key` = HMAC(APP_SECRET) (shown in Settings → Notifications). `tick` auto-logs due bills and sends what's due, up to 3 h late, deduplicated by `notification_log` keys. `public/sw.js` shows notifications and caches nothing.
- Backups (`backup.ts`): the owner sets a passphrase (Settings → Backup); a scrypt key from it is stored encrypted with APP_SECRET in `app_setting` (`backup:<user>`), never the passphrase. A backup file is JSON {format 'paisa-backup', kdf, iv, tag, data = AES-256-GCM(gzip(all book tables))}, openable with the passphrase alone (no APP_SECRET), so it restores into a fresh instance. `.github/workflows/backup.yml` calls `POST /api/cron/backup` (cron key) nightly at 02:00 IST and keeps only the newest `paisa-backup` artifact. Restore (`/api/backup/restore`, needs login password) replaces the book in one transaction, keeps a safety copy (`backup-before-restore:<user>`), and skips audit_log and Kite/Splitwise links. **Any new table that references `book`/`account`/`txn` must be added to `TABLES` and the delete order in `backup.ts`** (and to the demo reset).
- Copilot tools (`copilot-tools.ts`): with ANTHROPIC_API_KEY set, `copilot.ts` runs a manual tool loop (Claude Opus 5.5, server-side refusal fallback, strict tools, max 8 steps). Tools only read; `draft_transaction` returns a draft that the web shows as a "Review & add" card opening QuickAdd pre-filled (`QuickAddPreset.draft`). Amounts reach the model in whole rupees. Without a key, the local pattern engine answers.
- Motion: CSS in `themes.css` ("Living motion"), helpers in `motion-fx.ts` (confetti, saved check, scroll reveal). Don't wrap navigation in View Transitions: an update callback that waits on requestAnimationFrame never resolves (rendering is paused), which froze every tab switch until the browser's timeout, swipe rows in `components/Swipe.tsx` (the only use of the `motion` library). Everything must stop under prefers-reduced-motion.
- Category picker: `components/CategoryPicker.tsx` (recent, search, category → subcategories, add in place, ✎ Edit to rename a subcategory in place). `PATCH /api/categories/:id` also takes `parentId` to move a subcategory under another top-level category of the same class; the move copies the new parent's `not_income`.
- Theme default: Monotone, light (`theme.ts` DEFAULTS and the inline script in `index.html`, which must agree). Prefs carry `v`; bumping `PREFS_VERSION` moves every device to the defaults once.
- Spacing: the last block of `themes.css` ("Comfortable spacing") sets the page rhythm (`.page-anim > * + *`, sections, cards, rows, fields). Adjust spacing there rather than per page. Transaction search (`q`) also matches category and parent-category names.
- Privacy mode (eye button: Home header, sidebar, floating on phones, Shift+H): `money()`/`compact()` in `lib.ts` return a fixed mask; `maskText()` hides amounts inside server-written text (insights, health tips, copilot answers); `maskNum()` for bare numbers that give amounts away. Any new amount on screen must go through these. Stored per device (`paisa.privacy`); the shell re-renders on the `paisa:privacy` event.
- Income vs money in: only categories where `counts_as_income(account)` is true count as income (SQL function, migration 008). Income categories flagged `meta.not_income` (and their children) are money in, not earnings: "Money in (not income)" › Repayments / From family / Reimbursements / Other money in, plus Refunds & cashback and Gifts received. Statement imports default unknown credits to "Other money in". Use `counts_as_income(a)` in any new income query.
- Security headers (`app.ts` onSend): strict CSP (`script-src 'self'` + hashes of index.html's inline scripts, `connect-src 'self'`, no framing), HSTS, nosniff, no-referrer, `cache-control: no-store` on /api. Nothing may load from a CDN: OCR (tesseract worker, core, eng data) is copied into `web/public/ocr` at build (`web/scripts/copy-ocr.mjs`). If you add an inline script to index.html, the hash updates automatically on restart.
- Another owner (e.g. a partner) gets their **own** copy on their own GitHub/Neon/Render. `scripts/publish-for-partner.sh "what changed"` exports HEAD into a clone of the private clean repo `paisa-os-app` (one new commit, never this repo's history) and pushes; she forks it and taps Sync fork to take updates. `scripts/export-for-new-owner.sh <folder>` does the export itself: removes personal files (sheet snapshot, H&M OCR fixture), strips blocks and spans marked as personal (marker syntax: see the script), and refuses if anything in the git-ignored `scripts/.personal-patterns` remains. Mark any test or list built on the owner's real data with those markers. Never add multi-user access to one instance for this; separate instances are what make cross-access impossible. Guide: `docs/NEW-OWNER.md`.
- Password recovery: set `RESET_OWNER_PASSWORD` (10+ chars) in the server environment, restart, log in, remove it (`server.ts`).
- Goal contributions are earmarks, not ledger postings: they never change balances or spending. A boost on an account-linked goal creates a real transfer.
- Idempotency by `txn.external_ref` (unique per book): `rec:<rule>:<date>` for recurring, `stmt:<ref|hash>` for statements, `sw:<id>` for Splitwise. Keep new integrations on this pattern so re-running never duplicates.
- `apps/web/src/`: React PWA. Browser-side parsers (no external AI): `voice.ts` (sentences), `statement.ts` (bank CSV/TXT), `receipt.ts` (Tesseract OCR, lazy-loaded), `cas.ts` (pdf.js, lazy-loaded). `styles.css` holds base tokens; `themes.css` holds the 12 themes (`html[data-theme]`), light/dark (`data-mode`), contrast (`data-contrast`) and the compact density. `theme.ts` stores the choice per device. Income is `--inc` (blue) and expense is `--exp` (red) in every theme. Shared dashboard pieces are in `components/Planner.tsx`.
- Demo reset (`seed-demo-data.ts`) must delete every table that references accounts or txns before deleting them (stuff_item references txn). Update it whenever a new table points at `account`.
- `db/migrations/`: append-only SQL.
- `render.yaml`: the Render blueprint.
